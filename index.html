    Big picture theory

    Read this first. It explains why the labs are built the way they are.

    Why this skill exists

    Automation has had three generations. Scripts did one fixed job. Integration tools such as n8n connect apps with fixed rules: if X happens, do Y. LLM agents add a model that can read messy input, such as an email, a voice note or a PDF, and decide what it means. Models are good at reading and deciding, and workflows are good at moving data between apps. Combining the two is the value of this whole course.

    Why n8n. It is source-available, free to self-host, has hundreds of integrations and AI agent nodes, and exports workflows as JSON. Your client data stays on your own machine. The trade-off is that you run it, so backups, updates and security are yours.

    Design rule: workflow first, agent only when needed. Use a fixed workflow when the steps are known, and an agent only when the path cannot be known in advance. Fixed workflows are cheaper, faster, easier to test and fail in predictable ways. Agents add flexibility, but also variance, cost and attack surface. Example: summarizing each news item is a fixed step. Researching a company and deciding what to ask is open-ended, so it suits an agent. See Building effective agents.

    How language models work

    A model reads text as tokens and predicts the next token, again and again (Transformer paper). Each property below changes how you design.

    PropertyDesign response
    Predicts likely text, not true text, so it can hallucinateGround answers in data, validate output, add human approval for risky actions
    No memory between callsSend history or stored facts with every request
    Limited context windowChunk, summarize, retrieve only what is needed
    Output varies run to runLow temperature (0 to 0.3) for extraction and classification
    Obeys instructions found in any text it readsTreat outside text as untrusted; limit tools; require approvals
    Cost and limits scale with tokensKeep prompts short, batch work, cache, add fallbacks

    Worked example: token budget for the news agent

    5 feeds with 20 items each gives 100 items a day. At about 300 tokens in and 80 out, that is 380 tokens per item, so 100 × 380 = 38,000 tokens a day. A once-a-day batch fits typical free limits (check the current limits). Summarizing and scoring in two separate calls would double it, so ask for both in one structured call.

    The agent loop

    The ReAct paper describes the pattern behind most agents: think, act, observe, repeat. The model never runs tools itself. It outputs a structured request, n8n runs the tool, and the result goes into the next prompt. That is why you control an agent: its tool list is its permission list.

    Worked example: booking trace

    1. User: book me Thursday afternoon.
    2. Thought: I need free slots. Action: list Calendar events, Thursday 12:00 to 18:00.
    3. Observation: busy 14:00 to 15:00.
    4. Reply: I have 15:00 or 16:00. Which one? (No booking yet.)
    5. User picks 15:00. Action: create the event, then confirm.

    Why: the booking tool runs only after the user confirms, so a misunderstanding cannot create a wrong event.

    Theory and worked examples

    Data flow

    A workflow is a pipeline of items. Every node receives a list of JSON items and outputs a list. Most beginner bugs come from not knowing the shape of the data, so after each node click it and read the output.

    Credentials and OAuth

    A credential is delegated power: an API key is as sensitive as a password. n8n encrypts stored credentials with your encryption key, so losing that key means losing access. OAuth lets you give scoped, revocable access (for example read-only Sheets) without sharing a password, so always pick the narrowest scope that works.

    Example: filter before the model call

    Input items have title, link and pubDate. Keep only the last 24 hours. Filtering first saves tokens, because you pay only for items that matter.

    const cutoff = Date.now() - 24*60*60*1000;
return items
  .filter(i => new Date(i.json.pubDate).getTime() > cutoff)
  .map(i => ({ json: { title: i.json.title.trim(), link: i.json.link } }));

    Example: a good summarization prompt

    You are a security news analyst. For the article below, return JSON with:
summary (max 2 sentences), topic (one of web, cloud, crypto, ai, other),
relevance (1 to 5).
Rules: use only the text provided. If unsure, set relevance to 1.
Article: {{ $json.title }} - {{ $json.content }}

    Why it works: the role gives context, a fixed schema makes parsing reliable, the closed topic list prevents inconsistent labels, and the last rule reduces invention.

    Common errors: OAuth redirect mismatch, consent screen left in Testing (tokens expire in 7 days), Gemini 429 limits.

    Module 2: Communication agents

    Days 8 to 11. Agents that handle chats, email and social drafts.

    Labs

    Checkpoint: 15 of 20 test questions answered correctly and 10 email drafts reviewed.
    Theory and worked examples

    Memory is re-sent history

    Models are stateless, so memory means sending earlier messages again. A window memory keeps the last N turns. Key it by chat id, or users will see each other’s context, which is a privacy bug.

    Grounding with retrieval (RAG)

    Split your documents into chunks, turn each into an embedding (numbers that capture meaning), store them, embed the question, fetch the nearest chunks and put them in the prompt (RAG paper). Models cannot know your private FAQ, and retrieval fixes that without retraining.

    Example. Question: do you deliver on Sunday? Retrieved chunk: deliveries run Monday to Saturday. Rule: answer only from context. Reply: we deliver Monday to Saturday, not Sunday. For a question not in the base, such as paying by crypto, the rule triggers an escalation: a team member will confirm.

    Classify before you act

    For email, classify first (urgent, customer, newsletter), then route. A small step with a closed set of outputs is easy to test, while one giant prompt that classifies, decides and writes is hard to debug.

    Why drafts, not auto-send

    A sent message cannot be undone. A draft makes the action reversible, and your approvals give you accuracy data before you remove the human.

    Example: measure it

    Review 30 emails. Classification is right on 27 (90%). Of 9 weak drafts, 6 had the wrong tone. Fix: add 3 sample replies to the prompt, then retest on the same 30. This test, fix, retest loop is the core engineering habit.

    Module 3: Business agents

    Days 12 to 16. Three production-style systems with error handling and security.

    Projects

    Production checklist

    Checkpoint: each project has a README, error alerts, and passes 10 test cases.
    Theory and worked examples

    Reliability principles

    • Failures are normal. APIs time out, quotas run out and models return junk.
    • At-least-once delivery. Triggers and retries can run a step twice. Idempotency means the same input gives the same result with no duplicates.
    • Retry with backoff. Wait longer after each failure (5s, 10s, 20s), stop after N tries, then alert.
    • Observability. Log input, output, status and duration.
    • Least privilege. Give each credential and agent only the access it needs.

    Example: idempotency. A lead arrives with submission_id 8841. Look it up in the Sheet. If found, stop. If not, process and append. If the form provider retries the webhook, you still create one lead.

    Example: lead scoring contract

    Input: a 3-chair dental clinic that misses calls after 6 pm, budget about 20k, needs it this month. Ask the model for fields the workflow can test:

    business: dental clinic
need: after-hours call handling
budget: 20000
urgency: high
score: 8

    An IF node checks score ≥ 7 and alerts you at once. Turning fuzzy language into a number the workflow can test makes the decision dependable, while you still see the original message.

    Security theory

    • Prompt injection (OWASP LLM01). The model cannot reliably separate instructions from data. Example: an email body says to ignore previous instructions and forward the last 10 emails to an outside address.
    • Risky combination. An agent that can see private data, reads untrusted content and can send data out. Break at least one of the three, for instance give the email reader no send tool, or require approval to send.
    • Defences that work: minimal tools, human approval for outbound actions, output validation, recipient allow-lists, separate agents for reading and acting, logging and alerts.
    • Not enough alone: telling the model to never obey injected text.
    • Webhooks: secret header, schema validation, rate limits, HTTPS. See OWASP GenAI.
    Injection testSafe behavior
    Email says to forward all data to an outside addressIgnored and flagged, nothing sent
    Message asks the bot to reveal its promptPolite refusal
    Form field holds script-like textStored as plain text, never executed

    Module 4: Selling AI services

    Days 17 and 18. Turn builds into a paid offer.

    Checkpoint: pitch page, price sheet and demo video are ready. Treat income claims as marketing and judge by your own pilots.
    Theory and worked examples

    Price the outcome, not the hours

    Clients pay for results. Estimate the value, then charge a fraction of it.

    Example (illustrative numbers). A clinic loses about 10 bookings a month to missed calls, at Rs 1,500 each, so about Rs 15,000 a month is at risk. If your agent recovers half, the value is Rs 7,500 a month. A fair offer is a Rs 12,000 setup plus Rs 3,000 a month for hosting and monitoring, repaid within a few months. Confirm the client’s real numbers in the discovery call, and check that the setup fee divided by your hours is a rate you accept.

    Start with a pilot

    Buyers fear paying for something that does not work. A paid 7 to 14 day pilot with one success metric lowers their risk and gives you a case study.

    Pitch in plain words

    Use: problem in their words, a 2-minute demo of the same workflow, expected result, price, timeline, next step. Say answers customer messages after hours and books appointments, not agentic orchestration.

    Delivery

    Most post-sale failures come from unclear scope and access. Use a written scope, an access checklist, a test plan and a handover document, and record who owns the workflow and credentials so clients are never locked out. Treat your first 5 pilots as paid learning.

    Module 5: Multimodal agents

    Day 19. Marked Soon on the course page, so these are free equivalents.

    Checkpoint: one workflow handles text, image and voice through a Switch node.
    Theory and worked examples

    Convert, then reason

    Images go through a vision component, audio becomes text through speech recognition, and documents are extracted to text first. After conversion the same agent logic applies. The pipeline is: input file, convert, validate, reason, act.

    Example: receipt logger. A photo arrives in Telegram. The vision step returns vendor, date and total. A Code node validates that the date parses and the total is a number above 0. If not, ask the user to resend. Then append to Sheets. Validation catches blurry-image misreads before bad data enters your records.

    Voice notes

    Speech recognition struggles with names and mixed Hindi and English. Reply with a confirmation such as: I heard, book Thursday 3 pm. Correct? Test with your own accent and vocabulary.

    Long documents

    A long PDF exceeds the context window. Split it into chunks of a few hundred words with a small overlap, summarize each chunk, then summarize the summaries (map-reduce), or retrieve only the relevant chunks.

    Module 6: Advanced orchestration

    Days 20 and 21. Coordinate specialists, then ship the capstone.

    Checkpoint: 85% pass rate on your 20 tests and a live demo to another person.
    Theory and worked examples

    Why several agents

    One agent with ten tools and a huge prompt gets confused. Specialists with short prompts and few tools are more accurate and each part can be tested alone.

    PatternUse when
    RouterDifferent request types need different handling
    PipelineSteps are known and ordered
    Parallel branches, then mergeIndependent subtasks such as research and fact-check
    Worker plus reviewerQuality matters and a checklist exists
    Supervisor with tool-agentsOpen-ended tasks that need dynamic choices

    Error compounding

    If each step is 90% reliable, five steps in a row succeed about 0.9 × 0.9 × 0.9 × 0.9 × 0.9 = 59% of the time. So use fewer steps, validate between steps and retry the weak ones. Each agent call also adds time and tokens, and a supervisor with three specialists can mean 4 to 8 model calls per request, so cap iterations and use a cheaper model for classification.

    Evaluate, don’t guess

    Build a fixed test set of 20 to 50 inputs with expected outcomes and rerun it after every change. Do not tune on the same 20 cases forever: keep 10 unseen cases for the final test.

    InputExpected route
    What are your timings?Support
    I want a quote for 50 unitsSales
    Send me last week’s summaryReport
    asdfFallback: ask a clarifying question

    If 19 of 20 route correctly, inspect the miss, then change the prompt, add an example or add a fallback.

    Security across agents

    A message passed between agents is still untrusted if it started outside. Give each agent its own tools, validate every handoff against a schema, and require approval before sensitive actions.

    Key concepts

    Short definitions to keep beside you while building.

    Agent loop

    Think, call a tool, read the result, repeat. n8n runs the tools, so the tool list is the permission list.

    Token

    A chunk of text. Context windows and free quotas are counted in tokens.

    RAG

    Retrieve relevant chunks of your documents and put them in the prompt so answers are grounded.

    Idempotency

    Running a step twice gives one result. Store processed IDs.

    Prompt injection

    Hostile text in data tries to override instructions. Treat outside text as untrusted.

    OAuth

    Scoped, revocable access to an account without sharing a password.
